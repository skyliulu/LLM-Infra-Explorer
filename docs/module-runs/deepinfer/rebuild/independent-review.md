5. 进入 MoE 内核：观察时刻 0、3、8；在时刻 3 比较整批等待与 A 回传/B 计算交叠，读假设；返回 Decode。
6. 进入服务调度：对照固定两份资源上的 FIFO 和阶段分离；关闭分离并读适用条件。进入 Decode 实例，读同步/异步 CPU 与设备时间线及自回归依赖；返回服务调度，再回到整套服务。

## 阅读后可重建的解释

页面使我能给出的答案是：续聊有长历史但新输入少，先把已有 KV 从共享存储送到当前 Prefill 实例，便可只算未命中后缀；这把重算换成了存储和传输。生成阶段每请求每步贡献少量 Token，宽 EP 把多个卡的 Token 汇到同一套分片专家上，同专家可以一起使用一份读入的权重；热点副本改善最忙卡，但增加权重份数。MoE 再按块生产/消费，使分发、计算、回传跨块交叠。服务层分别安排 Prefill 与 Decode，能改变长输入对生成的排队干扰，并允许不同并行配置；实例内部再让 CPU 更新与下一轮设备工作交叠。它们最终增加延迟目标下的有效服务量，才可能降低单位 Token 成本，不能把示意倍率相乘。

无效或变弱条件也可从页面得到：低缓存命中、低并发、慢互联会分别削弱复用和交叠收益；存储、冗余专家、高速网络与备用容量有成本；分离阶段本身不消除计算，也可能让输入工作更晚结束。收入不等于利润，公开离线引擎不等于完整线上服务。

## 上下层映射与摩擦

- 3FS/Prefill/Decode 是总览上的同一组件，展开历史时 H/N 块持续同名，返回后命中配置仍反映在总览，映射清楚。
- Decode 的“专家分发→计算→合并”继续下钻成内核的相同三类操作，父层与子层的问题确实变窄；CPU/GPU 分支也属于服务调度下的 Decode 实例，返回路径正确。
- 第一轮初见的 R→T1 映射缺失，owner 已在同轮 HMR 后补入可见文本：“T1 对应请求 R 本轮的输入表示，其余 T 来自同批其他请求”；已实际读到补充，待稳定版复核。
- **层次摩擦（P3，待稳定版复核）**：内核层 A/B/C 未定义它们和父层 T1…T32 的关系。时间线机制可理解，但“同一次 MoE”的对象连续性要靠读者自行补出。建议明确它们是示意 Token 块，并给出包含父层某个 T 的映射，不需另加完整模拟器。
- **阅读摩擦（P3）**：服务调度中的 P1 与 D1 容易先被理解为同请求前后阶段，而 D1 从时间 0 开始。展开条件后才明确它们是互相独立的输入工作与已经生成的请求。建议把这个必要读图定义移到时间线前或图例。
- **状态文案摩擦（P3）**：关闭 P/D 分离时，两条图完全同为 FIFO，正文仍写“这个例子里，生成更早完成，输入侧却结束得更晚”；此时正文应明确它在描述“启用分离后的比较”，或随开关改变。
- **时间状态摩擦（P3）**：MoE 时刻 8，上轨 A/B 已计算完、等待回传，却统一显示“待处理”。建议用“待回传”保留读者刚观察的进展。
- Dark 桌面实际表面、文字、图形对比可读；EP2 会使较多组延伸到屏外，但不是同一尺度数据被挤坏。主题/语言/响应矩阵不在第一轮独立阅读验收范围内。
