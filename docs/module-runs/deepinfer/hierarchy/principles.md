# DeepInfer：从框架原理决定章节分工

2026-10-27. Redesign authorized by the user's hierarchy/focus/copy feedback. The preceding depth trial remains historical; a feature inventory was useful research but unsuitable as the page structure.

## 本章要回答的问题

一个推理引擎，怎样把不断到来、长短不同、进度不同的请求，组织成持续执行的批次，并把结果正确接回下一轮？读完后，应能说明请求、批次、执行器和状态之间的关系，以及异步调度为什么能减少 GPU 空等。

这是一道框架问题。不能只留一张调度动画，也不需要在这里重新讲完框架依赖的所有算法。源码用于核对行为；叙述顺序由原理和职责决定。

## 分层与具体对象

1. 服务位置：服务入口交出准备好的 Token/参数 → 引擎；引擎读写历史和状态 ↔ 缓存。完整服务与公开离线引擎的范围分开说明。
2. 引擎职责：队列保留请求进度 → 调度器给出本批请求/位置/输入长度 → 执行器整理设备张量并调用模型 → 结果处理更新输出、结束与资源状态，再回到下一轮。
3. 执行组件：Attention 和 MoE 在模型每层重复，最后采样/验证；框架整理每个请求的历史、组织专家通信，接受确定的 Token/长度。子组件返回后，应能解释它为什么属于父组件。

一级上下文和返回路径通过面包屑保留；结构图与下面的逐步运行是不同交互对象。图用于解释职责，下方轨迹用于观察一个批次怎样推进。默认入口是引擎层；可以回到服务层，或进入设备执行层。

## 证据与限制

沿用已核对的官方 DeepInfer `553741557a57df44a46fb3ab72b6aafeaf945337`：`doc/inference_deployment_qa.md:23/129/290` 提供服务定位，`scheduler.hpp:275/351/559` 提供批次与预算，`llm_engine.py:860`/`worker.py:89` 提供循环与异步，`model_runner.py:308/562` 提供执行准备和图复用，`attn.py:752`/`mlp.py:565` 提供执行组件接口。细证据留在已有 `technical-analysis.md`，不把其 19 项研究清单全部变成页面。

保留原请求模型的明确缩小条件：同步 NORMAL、nextn0、两个生成名额、充足缓存、每轮尝试输入；只用于解释推进顺序。异步时间图仍用假设时长，不预测性能。没有运行 GPU/NPU 推理。静态架构关系通过源证据和导航检查核实，不强行虚构数值实验。
