## Findings

### F1 — P2, central implementation-fidelity mismatch: early remote writeback is presented as completed combine

**Local locations:** `src/components/deepinfer/lesson-model.js:40`; `mechanism-model.js:13–15`; `MechanismPanels.jsx:10` and `:28`; `ConnectedReport.jsx:19,30,43`; `SystemAtlas.jsx:12,19`. In particular, the inspector's English `returned` is “Combined result received” (Chinese “合并结果已到达”), and the parent interface promises combined results on source ranks.

**Source:** [SM100 FP8/FP4 mega kernel:1273–1354](https://github.com/deepseek-ai/DeepGEMM/blob/1fc9c66975ee322d628b3288534ca0e9ce12a64d/deep_gemm/include/deep_gemm/impls/sm100_fp8_fp4_mega_moe.cuh#L1273-L1354) writes GEMM2 output directly into remote `combine_token_buffer` slots. This is genuine early partial-result transfer. Subsequently [lines 1410–1441](https://github.com/deepseek-ai/DeepGEMM/blob/1fc9c66975ee322d628b3288534ca0e9ce12a64d/deep_gemm/include/deep_gemm/impls/sm100_fp8_fp4_mega_moe.cuh#L1410-L1441) grid-synchronize all local L2 writes, publish rank-level readiness, and wait for selected expert peers before reading and reducing those slots into output.

**Reproduction/counterexample:** `getKernelBuffers(4)` reports fused A `returned:true`, B `compute:'computing'`, and C waiting for compute. Put A/B/C on the same expert-owner rank (the current model does not encode a different placement). Its final A reduction cannot pass the pinned implementation's readiness gate until that rank has completed B/C L2 writes. A's remote partial output may already exist, but that is a different state. Even if one imports the preceding top-1 simplification, top-1 removes the arithmetic sum over multiple experts; it does not remove this implementation's rank-wide readiness gate. With real top-k, a token also needs all selected expert contributions.

This is a local per-rank L2 barrier followed by selected-peer readiness, **not** a global EP/all-requests completion barrier. An early token may finish while an unrelated rank still computes, provided its local combine path and all selected expert-owner ranks have reached the required boundaries. The current one-ordered-compute-lane ABC display has no rank/top-k-slot identity with which to establish that alternative mapping. The finding is premature final readiness in its represented same-resource pipeline and missing source correspondence, not a universal prohibition on token completion overlapping any computation anywhere.

**Impact:** The central overlap claim is plausible, but the view teaches an overly fine final-consumption boundary under the Mega MoE name. An “illustrative timing” disclaimer cannot repair a wrong dependency. This is P2 rather than an urgent production bug, but blocks a technically complete implementation-aligned verdict for this mechanism.

**Bounded repair:** Retain early overlap bars as “GEMM2 partial-result writeback” into per-source/top-k slots. Add a distinct final readiness/combination step after the relevant owner-rank L2 work; distinguish result-present from result-consumable. The minimum repair can remain a small three-block model without reproducing all SM scheduling. Alternatively explicitly scope the whole view to a generic pipeline and avoid presenting its per-block final combine as the pinned implementation. Preserve the correct fact that dispatch/GEMM work and NVLink output stores can overlap.

### F2 — P2, implementation-depth gap: the EPLB physical layout cannot exist in the selected implementation

**Local locations:** `src/components/deepinfer/lesson-model.js:23–24,34`; displayed physical boxes and extra replica count in `ExpertComparison.jsx:12–15`; EPLB prose in `ConnectedReport.jsx:18,29`.

**Source:** [DeepInfer `mlp.py:207–216`](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/mlp.py#L207-L216) gives every EP rank the same number of physical slots and asserts total physical experts divisible by EP size. [EPLB `resolve_num_extra_experts`:21–28](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/eplb/__init__.py#L21-L28) rounds the configured minimum accordingly. [DeepGEMM buffer API:41–50](https://github.com/deepseek-ai/DeepGEMM/blob/1fc9c66975ee322d628b3288534ca0e9ce12a64d/csrc/apis/mega_moe.hpp#L41-L50) enforces the same invariant. Deployment Q&A lines 95–103 describes fixed redundant slots, history-based reassignment and weight shuffling.

**Reproduction:** Select input/rank=4, hot E1, replication on. EP8 shows 11 total physical experts with rank capacities `[1,2,2,2,1,1,1,1]`; eight logical experts plus the displayed three extras fails `11 % 8 == 0`. The corresponding source layout needs at least eight extra slots (16 total, two/rank) if one begins from eight logical experts and requests any extras. The toy's count and apparent placement are not a shrunk instance of that source rule. Switching replication on for batch=1 is also inert, although the label does not explain that configured slots are not being modeled there.

**Impact and scope:** “Replicas can spread a hotspot, at a memory/movement cost” is correct, and evenly round-robin distributing toy tokens is a valid ideal policy. Neither requires implementing the real rebalancer. The defect arises when the visible physical layout/extra count is offered as this runtime's EPLB layout without its fixed-slot condition. This is a depth/ownership constraint, not a demand for all implementation details.

**Bounded repair:** Keep the simple no-replica comparison. For EPLB, either model a fixed divisible physical-slot budget and show reassignment (plus identify simplified token-to-replica selection), or explicitly label the unequal-capacity layout as an abstract replication example with a concise statement that DeepInfer reserves equal slots per rank. Do not imply the three-extra count is a supported EP8 allocation. A faithful deeper branch should retain logical→physical mappings and slot lifecycle, not necessarily production window lengths.

### F3 — P2, buffer identity mismatch: the displayed symmetric input is filled by the wrong stage

**Local locations:** `src/components/deepinfer/mechanism-model.js:11`; `MechanismPanels.jsx:9–10,28`. At tick zero the displayed “Symmetric input buffer” is empty/writing, and dispatch creates it; it then becomes consumed by expert computation.

**Source:** [DeepInfer `mega_moe_forward`:535–554](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/mlp.py#L535-L554) writes gate metadata and ensures the original input already resides in `sym_buffer.x` before calling the mega kernel (FP8 previous norm/cast writes there; BF16 explicitly copies). The pinned kernel [lines 434–436,550–555](https://github.com/deepseek-ai/DeepGEMM/blob/1fc9c66975ee322d628b3288534ca0e9ce12a64d/deep_gemm/include/deep_gemm/impls/sm100_fp8_fp4_mega_moe.cuh#L434-L555) pulls remote original inputs into the expert owner's local L1 ring buffer. GEMM1 consumes that received L1 buffer after its ready count, not the source-rank input as newly produced by dispatch.

**Counterexample:** Inspect A at time=0/1. If the box means the caller's symmetric source input (`sym_buffer.x`), it must be populated before launch; the model says writing then ready during launch. If it means `l1_token_buffer`, its producer/consumer phases make sense but its displayed ownership and identity are underspecified/misleading.

**Bounded repair:** Rename the tracked box to the received expert-input/ring block and state its owner. Show the source symmetric input as already populated, or explain it briefly beside the chain. This repairs the ownership distinction without exposing a full memory map. Continue to distinguish “consumed” from physically freed; the existing disclaimer correctly does so.

## Valid simplifications and evidence limits

The unreplicated weight example is useful: same 32 tokens and eight ranks, uniform routing, EP2 activates 32 physical copies versus EP8 eight; each selected E1 copy has one row versus four rows at the single EP8 copy. Total token–expert operations remain 32. At one token/rank under uniform routing both activate eight copies, so the counterexample correctly demonstrates that widening need not reduce this ideal active-copy count. Hot E1 without replication gives EP8 max load 16 versus EP2 four. These are model-derived explanatory quantities, not source measurements.

These results were independently checked against token IDs, origin groups and expert assignment, and reproduced by importing the pure chapter model in Node. All combinations of batch `{1,4}`, routing `{uniform,hot}` and balance `{false,true}` were inspected for both EP values. No upstream Python/CUDA code was executed. The test checks accounting and boundaries; it does not validate real device traffic.

The single `X_e[m_e,k] × W_e[k,n]` formula in the expert view is valid linear-algebra notation for the invariant weight shape versus variable input rows. It need not show actual packed-transposed weights to explain amortization. At implementation depth, however, it would need two projections, SwiGLU, weight/activation precision and scale layout, routing weights and shared-expert handling. Those omissions are not by themselves false claims: the present expert view is explicitly a small top-1 shape illustration. DeepInfer repacks weights via `_convert_mega_moe_weight` and allocates a persistent symmetric workspace; it does not reread a separate full expert object once per displayed token.

The serial path is identified as a whole-batch barrier baseline and both copy languages acknowledge that separate operators may already overlap. The arbitrary 1/2/1 durations do not establish measured Mega MoE benefit; the current timing disclaimers are appropriate. Kernel input readiness and GEMM1→GEMM2 finer channel dependencies are source-supported; a simplified aggregate compute stage is acceptable provided its final-output boundary is repaired.

No rendered acceptance, hardware timing, precision tolerance, production scaling, or numerical equivalence verdict is provided. The assessment supports the main Wide-EP amortization principle with explicit limits; it does not support calling the current Mega MoE buffer/return view implementation-aligned until F1 and F3 are addressed or its scope is narrowed. F2 needs either source-faithful capacity or a visible conceptual boundary before claiming EPLB implementation depth.

## Follow-up challenge and corrected finding status

This clarification preserves the original assessment above for review history and supersedes its stronger F3 wording and any conclusion that F3 proves an initialization bug.

**F3 is an ownership-mapping ambiguity, not a demonstrated wrong-stage initialization defect.** Re-reading the actual copy, the box says only “对称输入缓冲” / “Symmetric input buffer”; it never identifies `sym_buffer.x` or assigns this object to the source rank. Therefore it can consistently denote the received L1 ring block, for which dispatch filling followed by GEMM consumption is correct.

Further primary-source tracing supports that interpretation. [DeepGEMM `SymmBuffer.__init__`:42–76](https://github.com/deepseek-ai/DeepGEMM/blob/1fc9c66975ee322d628b3288534ca0e9ce12a64d/deep_gemm/mega/__init__.py#L42-L76) obtains one allocation using the symmetric-memory allocator for multi-rank groups, establishes the rendezvous handle, and slices all buffer views from it. [C++ API:96–148](https://github.com/deepseek-ai/DeepGEMM/blob/1fc9c66975ee322d628b3288534ca0e9ce12a64d/csrc/apis/mega_moe.hpp#L96-L148) creates both original `x` and received `l1_acts` tensor views from that same raw buffer. [MegaMoEBuffer layout:400–453](https://github.com/deepseek-ai/DeepGEMM/blob/1fc9c66975ee322d628b3288534ca0e9ce12a64d/deep_gemm/include/deep_gemm/layout/mega_moe.cuh#L400-L453) places `input_token_buffer` and routed-expert `l1_token_buffer` at distinct offsets within it. Thus calling the received ring “symmetric” is not itself incorrect. The extra raw Python source is saved as `C:/Users/29043/AppData/Local/Temp/deepgemm-fidelity-1fc9c66/mega-init.py`.

The narrower issue is that the current display does not establish which of these buffers it tracks, its owner, or what the abstract A/B/C blocks correspond to. For intuition, the consistent receiver-ring interpretation is sufficient and should not be failed as a proved buffer-lifecycle error. For a branch claiming real implementation depth, explicitly identifying the received ring and its source is a bounded improvement and belongs alongside F1's missing rank/slot mapping. **Final finding count: two P2 source-fidelity findings (F1 and F2), plus this nonblocking depth clarification; no independently proved third runtime-semantic defect.**

**F2 scope clarification:** The ragged toy layout and round-robin token distribution are not numerically wrong as a generic educational replication example. The source mismatch is specifically the fixed equal-capacity slot budget and resulting physical-count/cost interpretation when taught as the selected DeepInfer EPLB implementation. The valid weight-amortization and hotspot principles remain valid. A conceptual-boundary statement may address that scope without reproducing the production rebalancer.

F1 remains a source-bound distinction between valid early partial GEMM2 writeback and the displayed final combined-result readiness. Its locality qualifications above remain essential. No additional GPU or browser validation was performed for this clarification.
