## 六节正文：每节 2–3 句，可直接作为主要说明

### 1. Prefill 与 Decode 各用合适的并行规模

Prefill 一次处理一段新输入，Decode 每轮只推进少量 Token，两边需要的批量和资源规模不同。官方部署把它们拆成独立资源池：Prefill 选显存放得下的较小 EP/DP 组（2–8），Decode 在高速通信域内用宽组（64–128）。每个 rank 的 Attention 保留本地请求和 KV；进入 MoE 时，Token 发往专家所在的 rank，算完再返回。

图应有：入口 → P资源池 → 状态/KV传递 → D资源池 → 输出；P/D内部各有“本地Attention → 分布专家 → 返回”的缩略关系。VE是可选输入支路，宜标“图像输入时”而非占据文本请求主线；不应完全把整个框架画成两框但又暗示覆盖全部服务。

### 2. Wide-EP 把 Token 汇到同一份专家权重

固定总卡数时，多个小 EP 组各自保存一套逻辑专家，也会各自读取其中的活跃权重；合成宽组后，同一份专家权重能服务更多请求的 Token。专家 GEMM 的输入因此增加了 Token 行数，权重的特征维度和总路由计算量没有随之缩小。这个收益需要足够并发；路由集中到少数专家时，还要靠冗余副本分担最忙卡的工作。

图应有：同一批Token和同样8卡的EP2/EP8同屏对照；高亮同一逻辑E1的四份/一份物理副本，以及每份实际收到的Token矩阵行。不要把“32→8读份数”孤立成结论卡。EPLB放在本图中的热点状态，副本占用和负载一起变化。

### 3. Mega MoE 让就绪的数据先算

路由确定后，Token 要经历分发、专家两次矩阵乘和 SwiGLU、结果合并。Mega MoE 把这些操作放进一个内核：输入块到齐即可交给计算，完成块可以回传，后续块继续执行。输入、环形中间缓冲和远端合并缓冲仍然存在；关键是生产者何时写好、消费者何时能读，而不是把通信或 HBM 状态全部删掉。

图应有：同一A/B/C块在输入缓冲→计算→结果缓冲→来源rank的实际占位；时间位置改变可读/可写/等待状态。可与整批屏障示意同屏，但注明真实分离算子路径已有部分异步重叠，不能把示意基线冒充固定实测基线。

### 4. 缓存共享后，请求不必返回原机器

持久块 KV 放在独立 3FS 上，每个 Prefill 引擎都能读取同一段历史，请求因而可以发给有剩余计算配额的引擎。入口先完成前缀匹配，命中数据再异步取到主机共享内存，按层经 GDR 装入 HBM；这些步骤各自有成本。SWA 窗口另存在产生它的机器主机内存中，需要目录定位或有界重放，不能与块 KV 当成一份整体读回的对象。

图应有：同一条R、同一前缀H，繁忙P-A/空闲P-B和共享3FS连接；用户选择“本地持有/共享可达”时可看到路由约束变化。CED只是恢复SWA的模型前提，挂在状态节点内，不成为另一条必读课程。

### 5. 调度看的是工作量，不只是请求数

Prefill 按上下文长度分桶，再根据已计算前缀和本轮输入量估计耗时，用时间预算决定 chunk 大小；DP 组内还会用最小预算限制整组步长。Decode 同时考虑请求数与 KV 总长度：前者影响专家批量，后者影响 Attention 负担，同样“两个请求”可能有很不一样的负载。CPU/GPU 异步执行随后填补主机处理的间隙，但不会解除上一轮采样到下一轮前向的依赖。

图应有：候选D-rank上的请求个数与KV长度两条尺；加入同一短/长请求时，比较只看请求数与兼顾KV的选卡和后果。P quota若做数值模型，必须标“人为二次成本示意”，真实官方拟合系数未给出，不能假装准确重现生产策略。

### 6. 性能图要在服务目标下读

官方曲线展示的是吞吐与单用户速度的取舍：同一批量下，宽组在图中同时更快、吞吐更高；增加并发则会让单用户速度下降、总吞吐上升。机制图解释这种变化可能从哪里来，官方测量才说明在给定模型、上下文与验证设置下实际得到什么。单位成本还要计入存储、互联和备用容量，155T/日与38美元/GPU小时是完整生产服务的量和收入，不能直接当作离线引擎的利润或回本周期。

建议结果面板常显而非末尾折叠：先高亮一个官方点对，旁边只展示该点对的两个坐标和比较条件，再用“回到专家/通信/调度”链接定位机制。不要把玩具读取倍率与测量吞吐倍率相乘。

## 官方 Pareto 图的三个安全读法

坐标：横轴 per-user speed，单位 tokens/s/user；纵轴 output throughput，单位 tokens/s/GPU。蓝色 EP64DP64、384+64 experts；橙色 EP8DP8、384+32 experts。点上数字是每个 DP rank 的请求数。

固定条件：context 131,072；nextn=3 fixed；per-token acceptance 75%（图注明对应 τ=3.25）。图片本身没有列出所有硬件细节，不能只凭仓库“支持SM100”推定这张图的完整硬件配置。

### 观察 A：同为每rank 64请求

- 蓝点约在 **250 tokens/s/user、16,000 tokens/s/GPU**。
- 橙点约在 **200 tokens/s/user、12,500 tokens/s/GPU**。
- 可见结论：在这个请求数下，宽组两项都更高，差距大约四分之一量级。两个点是同请求数比较，**不是同单用户速度比较**。建议直接用圆圈/引线标这两点，不在页面写更精确的整数或小数比。

### 观察 B：同为每rank 32请求

- 蓝点约在 **300 tokens/s/user、9,500 tokens/s/GPU**。
- 橙点约在 **220 tokens/s/user、7,000 tokens/s/GPU**。
- 可见结论：较小批量下，同请求数的宽组优势仍存在。仍然不能把这个点对解释为固定相同延迟或相同用户速度的收益；两个专家配置含有不同数量冗余副本，也并非只改一个开关的消融实验。

### 观察 C：一条曲线本身的取舍

蓝线由每rank 8请求增到256请求，图上的单用户速度从约325降到约100，而每GPU吞吐从约2,500升到约26,000。这个方向说明“吞吐最高”与“单个用户出字最快”不是同一个工作点，用户需要先指定服务速度要求再选点；不能拿两端相除称为框架加速。

### 不建议作为主证据的插值读法

在约200 tokens/s/user处，蓝线与橙线确有明显纵向差距，但蓝线在该x位置没有标注实测点。若画同速度垂线，应写“按图中连线插值的近似读数”，不叫同速度实测，不声称精确倍率。实现最稳妥的是只用A/B的原始标点做可点击注解，另保留“固定服务速度比较需要读整条曲线”的说明。
