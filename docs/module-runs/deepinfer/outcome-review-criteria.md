# DeepInfer 独立验收基线

2026-10-28；独立验收 agent 在新实现完成前制定。此文件记录评判依据，不把上一轮 QA 结论当作本轮通过证据。

## 读者最后必须能回答

核心问题：DeepInfer 与配套的 DeepSeek 生产系统，怎样在响应速度约束下，把同一批推理工作做得更省？哪些收益来自引擎，哪些依赖模型设计、硬件规模和服务设施？

读者应能连贯解释：少重复计算、少搬运数据、少等待，以及如何把这些局部改善变成整个服务的有效吞吐。不能只复述调度步骤或列出技术名词。技术章节的深度由这个问题决定，而不是“框架只能讲职责分工”。

## 本轮开始时观察到的问题

- `hierarchy/principles.md` 把主问题定成“请求怎样持续推进”，从源头将性能/成本主题缩成引擎生命周期；下层动画的丰富程度不能弥补主题偏移。
- `SystemExplorer` 默认从 engine/scheduler 进入；通用的队列→调度→执行→结果图，换成别的引擎仍成立，不能独立解释 DeepInfer 的性能特点。
- `system.css` 的 `.dh-map`、`.dh-node` 固定深色背景；没有 Light 分支。浅色模式黑色架构区是实质缺陷，不应因文字可读就通过。
- 顶层标题“一套推理框架，要把哪些事情组织好？”绕开读者想知道的性能和成本，中文也过于口语化、抽象。
- 当前可见内容缺少经济性口径，容易让读者把任一局部调度收益误当完整生产效率的解释。

## 官方资料已核实的边界

以官方仓库 `553741557a57df44a46fb3ab72b6aafeaf945337` 的 README 与 `doc/inference_deployment_qa.md` 为基准；2026-10-28 另读 main 的官方原文，关键口径一致。

- 官方将 kernels、通信、调度、缓存管理共同视为端到端性能因素。生产系统采用 E/P/D 分离与独立存储，公开版本是离线引擎，完整缓存管理、跨副本负载均衡并未完整开源。
- Prefill 推荐较小 EP/DP，Decode 推荐 Wide-EP；不能把两阶段的资源需求画成一样。Attention DP 与 MoE EP 是协同而非两个互斥模式。
- Q&A 将 Wide-EP 的作用解释为减少 MoE 专家部分每步的内存流量，并需要 EPLB；专家负载不均会让整批等待。低精度、融合计算和专用内核有具体工作，不能仅用库 logo 代替解释。
- 长时 KV 复用减少重复 Prefill；有取回、存储和容量成本。SWA bounded replay 有近似和边界，不能讲成无条件精确复用。
- 异步调度去掉 CPU 处理和下一轮调度造成的设备空隙，但不消除自回归依赖；它是其中一条路径。
- DSpark 可在本章说明其减少无效验证计算的作用并链接专题，不能把算法细节再平铺成独立课程。Q&A 的动态长度增益随并发变化，低并发表中也可能为负，不能给通用百分比。
- Q&A 的 155T tokens/day 与 $38/GPU-hour 是同一个线上生产系统的报告口径，后者注明谷价，且原文是 **revenue（收入）**。这不等于利润或开源引擎实测。不能把线上收入与离线 Pareto 图直接相乘或相除推论单位成本。
- README 的性能图是指定硬件和配置的阶段性吞吐/交互性权衡；不自动代表完整请求延迟、某云租价或用户部署的收益。
- 在读到的官方 README/Q&A 中未发现“一个月回本”结论。官方链接的知乎长文本次 web 读取 403；未获得原文不能补造。网页可解释什么条件下才可能推算回收期，但必须区分假设、收入、运营开支、硬件投入，净现金流不为正时不存在有限回收期。

## 新实现的验收标准

1. **主题明确且贯穿。** 首屏能看出要解释为何更快/更省，后续层级围绕这一论证下钻。去掉作者的研究笔记后，页面自己仍可回答核心问题。
2. **因果充分。** 至少覆盖重复 Prefill、设备计算/数据搬运、资源等待与跨卡不均等实际不同瓶颈；每个重要机制能说出改变了什么工作、如何改变、因此改善什么、代价/前提是什么。若省略一条，需说明为何不影响核心解释。无需在本章重讲每个依赖算法。
3. **层级服务解释。** 顶层给整体机制与资源关系；组件层说明框架如何整合；专用算法链接归属清楚且不掩盖本章必要解释。一个纯职责目录或独立 feature cards 清单都不通过。
4. **交互证明关系。** 至少有真实控制改变具体工作量/数据路径/资源占用并得到一致可观察结果；点卡片只换长文不算充分的核心机制交互。教学假设明确，不给虚构硬件加速比。各优化不能无依据相乘形成总加速。
5. **经济口径正确。** 38 美元放在生产服务上下文，收入与利润明确区分，不能默认归属于某种 GPU 或开源引擎；若提供测算，可见假设、单位、边界和反例需与纯模型一致。不以“一个月回本”为必须达成的宣传结果。
6. **自然中文。** 标题和正文连读具体、顺畅，有信息，不套抽象问句、不把验收/建模术语当读者文案。术语必要时给简短解释。
7. **主题视觉完整。** 浅色模式的主架构图、内容面板、选中状态、公式、滑块及局部演示均协调；不能把固定暗色大画布当品牌豁免。Dark 同样实看。桌面、平板、手机及两种语言不得以溢出/字小换取完整。
8. **独立证据。** 验收者自行审查新源文件、实际最终截图、控制动作和模型结果。记录具体问题、修复后证据与未覆盖范围。构建通过或文件数量不替代学习结果；没有达到标准就说明缺口，不能为了结束工作放宽标准。

本文件是预先制定的标准，尚未对新实现作通过判定。
