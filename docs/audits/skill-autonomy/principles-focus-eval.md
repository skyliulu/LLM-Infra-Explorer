日期：2026-10-27。任务是评估 skill，不是实现 vLLM 或修改 FlashAttention。仅写本文件；没有修改 skill、UI 或项目 QA 记录，没有操作浏览器、运行 build/model checks、读取上游源码或进行真实用户理解测试。下述实现与验收动作均为接到相应实施请求后会执行的路径。

实际阅读：新的 `analyze-technical-principles/SKILL.md`，当前 `develop-interactive-module/SKILL.md`、technical-analysis、content-and-math、AGENTS；定向检查 qa-checklist/autonomous-delivery，以及 registry/learning 配置和 FlashAttention、SpeculativeDecoding 的相关源码入口。未以旧评估结论代替本轮判断。

## 演练一：讲透 vLLM，站里已有 PagedAttention、投机解码、量化专题

### 先做的决定

把它作为框架层问题来处理。先查是否已有 vLLM 入口、既有页面和接受过的范围，再读用户所说的专题实际内容。不能只凭专题名称宣布它已经解释完某机制。本次有限 registry 检索没有得到独立的 vLLM/PagedAttention 路由；这是演练上下文与真实仓库的差别，实际工作需要进一步找对应章节/段落或记录缺口，不能编造链接。

不把调研结构定为 scheduler.py、worker.py、attention backend 等文件，也不预先选择所有优化的集合。先读一个固定版本的官方总体架构、执行/调度/缓存设计和相关论文，画出读者需要理解的责任关系，再用源码核实争议行为。vLLM 的具体调度规则、分块/混合处理、后端选择与并行支持会随版本变化；本演练没有查证这些当前细节，不能把以下候选设计当成已验证事实。

暂定主问题是：**“长短不一的生成请求不断进入时，vLLM 怎样安排下一批计算，并保存每个请求已经算过的状态？”** 读完应能解释一个请求如何进入计算、等待或继续，为什么请求结束会影响别人的执行机会，以及调度与缓存容量如何互相约束。先用官方架构校验该问题是否漏掉所选版本的主要组织方式，再定稿；不能用这个句子自行削掉用户的框架范围。

### 怎样分层，每层回答什么

| 层次 | 读者问题 | 本章要看见的关系 | 深入后如何返回 |
| --- | --- | --- | --- |
| 工作负载与约束 | 为何一批请求不能始终整齐地一起走？ | 请求到达、不同输入/输出长度、计算与 KV 容量的约束；先标出要改善的等待/利用率问题 | 保留当前请求集与资源概况，后续机制变化能在同一组请求上比较 |
| 框架组织 | 谁决定这轮做哪些工作，谁执行，谁保留状态？ | 调度、状态/缓存管理、执行器的责任和交换对象；根据选定版本确认真实接口 | 回到同一请求的位置、剩余工作和占用状态 |
| 一轮执行 | 某个请求为什么本轮获选，下轮可能等待？ | 从选择的 token/工作量，到执行所需 cache 映射、设备输入，再到结果/请求状态提交 | 显示本轮后哪些资源可释放、下一轮输入如何变化 |
| 必要局部机制 | 哪个决定改变了整轮执行？ | 深入调度预算、状态容量、必要的设备分工；每个局部选择都要回到本轮的组成/结果 | 不让用户在独立功能页中失去原请求和父问题 |

这张表是思考顺序，不强制做成四个页面或四张卡。首屏可让请求流、资源占用和本轮执行同时可见；点击当前请求查看它本轮所需的状态与调度原因。若只是点“scheduler”“cache”“worker”分别打开说明文字，仍未形成层次。

### 章节职责如何分配

| 概念 | 在 vLLM 章讲到哪里 | 深入的归属 | 不能被链接带走的内容 |
| --- | --- | --- | --- |
| 请求生命周期、调度与执行的配合 | 解释这里的完整因果路径，展示有证据支持的一轮选择/提交 | 本章 | 哪个对象做决定、受什么容量/依赖约束、结果如何改变下一轮 |
| PagedAttention / 分页 KV | 给足物理块/逻辑序列、映射输入、分配/释放与请求执行的关系；保留一个能观察容量影响的小例子 | 已有 PagedAttention 专题负责算法细节、寻址/读写的深入实验；必须先确认实际覆盖 | 调度器为什么需要这些状态、执行器怎样找到对应请求的历史；只放“了解分页”链接不够 |
| 投机解码 | 若所选版本支持且与主问题有关，说明额外候选工作如何进入执行、接受长度怎样影响下一轮和 cache 提交 | 投机解码专题负责提议、验证、拒绝修正与具体方案 | vLLM 在这个扩展下如何继续保持请求/缓存状态一致；不能仅画一个外挂 logo |
| 量化 | 说明选定数值格式怎样改变可用容量或后端约束；没有可靠模型就不显示量化速度收益 | 量化专题负责格式、尺度、误差及算法内部 | 本章模型究竟把哪些容量/约束作为输入；不能把位数直接等同于吞吐倍数 |
| 分布式执行 | 若是所选框架范围的重要部分，解释单执行器如何扩展到设备组，谁拥有状态，哪一步需要交换什么 | 并行专题负责 TP/PP 等算法内部 | 框架本身的控制/执行边界与必要同步，不能全丢给“并行策略”链接 |
| 单个 attention kernel 的内部流水线 | 交代它消费的输入/布局、产生的结果及选择约束 | FlashAttention/Flash Decoding 等合适专题 | 框架怎样交给它执行以及结果怎样提交；不在本章复制完整 tile simulator |
| DSpark 等具体方案 | 只有明确证据表明它与所选框架/当前解释有关，才交代接口作用 | 具体投机方案在投机解码章深入 | 不因另一个框架用过便认定 vLLM 也支持；也不为框架章引入全部方案细节 |

职责划分不会自动授权修改所有专题。读到专题缺内容时，记录准确的目标缺口，在本章供给理解接口所需的最小上下文。只有实际实施范围覆盖该专题，才在对应位置扩展；不在框架页复制另一套教程。

### 如何取证和交给渲染

实际会先产出 `principles.md`：主问题/学习结果、责任图、一个请求的因果路径、上表的职责决定、关键设计的收益和代价、固定版本证据。证据以官方论文/设计文档解释动机，源码只验证这版的选择条件、配置和不确定的行为。不会为了使用 Codebase Knowledge Builder 强制先做完整代码巡礼；若确实要追一条实现路径，再使用它做有界源码调查。

渲染交接给出具体对象与可证伪观察，例如：同一请求 ID 在队列、候选批次、cache owner 和返回结果中保持对应；新请求进入/已有请求结束后，读者能指出下一轮改变了什么。一次只改一个真实参数，保留能显示容量瓶颈或额外开销的情形。比较基线必须经来源确认，不能把一个刻意低效的“整批等待”模型说成所有普通引擎的实现。

真实验证要检查这些因果关系，不能只断言“总 token 数增加”：调度预算不超限，等待状态有原因，cache 释放/保留符合所选版本，执行提交后才推进请求。需要并行机制时，设备状态/通信反映它真实的分工。字节/等待轮数可以是标明假设的模型指标；真实 GPU 延迟需要测量，不能借动画时长推断。

**防止讲得太少的反问：** 不打开任何专题链接，读者能否解释请求 A 完成后请求 B 为什么能继续、B 执行需要的历史从哪里来、执行器返回什么才能启动下一轮？若不能，框架章自己的组织仍未讲清。若去掉分页/并行的接口说明会让图中的一个决定变得无法解释，这段就必须留在本章；不因“已有专题”删除。

### 需要用户输入吗，什么时候交付

vLLM 名称明确，不先问用户选专题深度/布局。版本可从既有资料固定；没有相关限制时自主选择一个明确版本并说明。只有多个已有目标冲突、关键证据不可取得，或补全主问题确实需要突破明确保留的页面范围时，才问具体问题。必要的 code/QA 工作在实施请求中应继续做到可用；本轮演练不实施。

完整交付需同时满足：责任图与因果解释完成、主体内容没有靠链接替代；用户能控制并观察真实模型关系；所有专题跳转描述与实际目的地一致；中文读下来能复述组织方式；当前版本模型、浏览器、双语/双主题/响应式及集成证据通过。仅运行 scheduler toy、堆更多 feature tab 或 build 成功均不能结束。

## 演练二：FlashAttention 补深度，目前只有“分块计算”

### 首先核对当前事实

按现有专题扩展处理，保留接受过的主要区域与控制。先读本章当前内容/模型、最新 QA 与邻近 attention 章节，再捕获相关 rendered baseline 后动布局。本次只查源码就已经看到现有 `FlashAttention.jsx` 有 HBM Q/K/V/O/LSE、资源指标、版本流水线与 inspector。因此“现页只有一句”在实际接手时可能描述另一版或教学感受；不能据此覆盖当前完整实现。

若现有资料能定位用户看到的版本，直接补真实教学缺口；只有多个目标仍无法定位时才问“你指的是当前工作区的 FlashAttention 章节，还是另一个页面版本？”源码里有卡片与字段也不能证明读者已经理解，仍需检查它们是否解释了因果。

### 主问题与分层

暂定主问题是：**“不把整张注意力中间矩阵写进显存，为什么仍能得到同一组输出？”** 补深度要补“为何成立、资源为何改变”，不能仅加更多“块”动画。

1. 从普通 attention 的实际依赖开始：Q/K 的分数、按行归一化、对 V 加权分别需要什么；让读者看见所比较基线会保存哪些中间量。基线要明确是否未融合、是否因果，输入和精度一致。
2. 再解释组织变化：片上空间有限，Q/K/V 分块进入计算，哪些状态留在片上，哪些结果写回；在整体 attention 输出里定位当前这一行/一块。
3. 深入真正的难点：新块改变一行的归一化尺度，旧的累计权重与输出也需要按新尺度调整。这里要解释跨块最大值、分母和输出累积量，显示前一块、当前块、修正后的状态。仅说“online softmax”仍然太浅。
4. 返回整体：遍历完成后与直接 attention 的输出按相同输入核对，并统计实际采用模型的读写。显示需要更多重算/状态管理的代价与适用限制，不把“不落完整中间矩阵”说成“没有二次计算量”或保证任何尺寸都更快。

假设首个基础实验采用经典前向机制。先用原论文/算法确认循环、状态与 IO 假设，再独立数值检查小 tensor、极端分数、不同分块和末块不齐的情况。所有“同一输出”说法需包含浮点舍入/容差，不能宣称位级一致。

### 什么在这里讲，什么不扩进去

- **本章负责：** IO 动机、受片上容量约束的分块组织、跨块归一化为何正确、最终输出和读写/重算代价。它们共同回答主问题，不能链接到 Softmax 或“kernel 专题”而跳过。
- **基础 attention 前置：** 链接通用推理/attention 原理可减少重复铺垫，但本章仍要用一个短、可见的 Q/K/V → 输出例子建立本次比较。不能要求先修完整前置课。
- **版本深化：** 如果页面已有 V2/V3/V4，保留其功能与真实差异，在基础机制成立后按版本的设计问题解释并行组织或搬运/计算重叠。实际论文与硬件范围需各自核实；不因本轮选择基础问题擅自删除既有版本，也不把全部硬件微架构塞进第一屏。
- **相邻优化：** 长 KV decode 的 split/reduce 交给 Flash Decoding；稀疏选择交给 Sparse Attention；数值格式完整课程交给量化。这里只保留对当前机制必要的区别和接口，不借相邻内容冲淡“跨块仍正确”这个缺口。

### 渲染交接与可证伪的操作

会把基础 toy 控制在能逐项核对的规模，选择一个后续分块产生更大分数的输入：推进到该块时，读者能看到最大值变化、旧累积量被重标定、当前贡献并入，而不只是高亮另一个矩形。再用“忘记修正旧状态”的可检查反例解释为什么单纯分别归一化后相加不够；错误路径如展示，必须清晰标识并不与真实算法混淆。

改变 block 大小应改变遍历/片上占用/读写账本，最终结果在容差内保持；输入不变时不能让比较两侧偷换 Q/K/V。支持因果模式时检查同一 mask，最后一块不齐不能访问越界。图、公式变量、数值累计、当前解释共同由纯模型推导。这里的“深”是能解释归一化和 IO 的因果，不是加类名、源文件行号或更多控制器。

会运行有意义的 oracle/model checks 与 `check:flash`、build、convention；路由/分享改变才补相应 checks。浏览器实际推进上述反例、末块/终态、模式切换/重置，确认图的 scale、公式和说明没有延迟错配。完整交付的双语/主题/宽度要求继续适用，聚焦修复则如实限定范围。**本轮这些均未执行。**

## 中文怎样验收：两章都要做的实际工作

先把技术关系和图上的对象定下来，再独立写中文，随后核对英文表达相同含义。可用的候选短句如下，具体术语与行为还须与选定来源/模型对齐：

| 位置 | 候选中文 | 检查读者能否指出什么 |
| --- | --- | --- |
| 框架首个问题 | “这一轮先处理哪些请求？” | 图上本轮选中的请求与未选原因 |
| 框架状态说明 | “请求结束后，释放的缓存块可以分给后面的请求。” | 实际模型在何时完成/释放/重新分配；不能跳过仍被共享或引用的块 |
| FlashAttention 归一化阶段 | “新块里出现更大的分数，先调整前面累积的结果，再加入这一块。” | 哪个值变大，旧状态按什么量调整，调整后哪一行继续累积 |
| FlashAttention 资源结果 | “完整的分数矩阵不用写回显存；最终输出仍会写回。” | 保存/不保存的具体 tensor，以及统计的 IO 项 |

阅读验收会按首屏→点击→当前说明→返回的实际顺序连读中文，检查每句话的主体、动作和对象能否在图上找到，标题是否自然承接上层问题；用一个非默认状态核对句子仍成立。缩短说明不能删掉必要条件，也不能让“它”“结果”失去指代。

独立审稿者若可用，给它页面与一项实际任务，例如“解释 B 为什么还在等待”“指出新块出现最大值后旧贡献怎样处理”，要求给出具体误解与位置；不能暗示期望判为好。没有真实学习者时只称 expert/copy review，不能说学习效果已测。实际中文 rendered QA 检查长标签、小字、换行/公式和按钮含义；i18n key 对齐、禁词计数与删字数不能单独通过这项验收。

“责任映射”“证据门槛”“教学主线”等管理词可以留在本报告与 run notes，页面主要叙述直接说对象与动作。保留必要来源和假设，但放在相关例子的紧凑说明中，不能用每段免责声明打断学习。

| 中文新增 semantic copy review，且要求上下文与来源随执行分支变化 | 漂亮短句掩盖真实条件，或“自然中文”被执行成禁词表/统一短句 | 本轮样句都绑定图上对象和非默认条件复核；需要实际连读/审稿/渲染证据。本轮无法断言它们在真实页面上自然可读，新规则的实际改善尚待 E2E。 |

结论限定为本轮行为观察：新 skill 能引导出有章节职责的原理分析，而不要求先完整解析代码；两个请求也不会因此自动变成“少讲”。仍须重点防止自选过窄问题、链接替代本章因果闭环，以及旧 run gate 把研究清单重新变成页面目录。上述风险为规则解释上的具体缺口，不是已复现的 UI 故障。
