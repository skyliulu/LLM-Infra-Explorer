# vLLM 吞吐与成本：前向决策测试

日期：2026-10-28。任务类型：assess，只交接设计，不实现章节。使用两个指定 SKILL.md 及其 technical-analysis、interaction-model、visual-grammar、content-and-math 参考；技术依据仅为一手只读资料。未读现有 DeepInfer 实现、历史验收或其他评估输出，未检索或执行开源代码。下面是独立生成的教学方案，不是现有页面的覆盖判定。

## 核心问题与期待读者回答

**核心问题：同一模型、硬件与输出质量要求下，vLLM 怎样让每 GPU 小时交付更多满足延迟目标的结果，这何时才会降低服务成本？**

期待读者能回答：vLLM 把可增长、可共享的 KV 状态与每步的实际计算需求连接起来，减少显存预留浪费和重复前缀计算，让更多请求共同使用执行资源；连续批处理及时补入工作，执行后端减少部分运行开销。这些机制共同改善有效产出，不能把任一容量倍率直接当成速度倍率。只有需求足够、延迟目标仍达标，且省出的容量能减少付费资源或增加有用产出时，单位服务成本才下降。单用户更快、吞吐更高、账单更低是需要分别验证的结论。

默认研究对象为 V1、标准自回归 Transformer 的在线文本服务，先以单 GPU 解释；这是起点，不能把全框架定义为单 GPU 离线调度器。多 GPU、服务前后处理作为外层约束保留。模型、精度、请求分布与质量要求在比较双方一致。

## 因果链与层次

| 从读者关心的结果倒推 | 控制量与设计决定 | 本章必须让人看见的机制 | 代价／失效条件 |
|---|---|---|---|
| 单位合格产出的资源成本下降 | 给定付费资源下的有效吞吐，或给定需求所需的资源数 | 合格请求计数、付费 GPU 时间与闲置时间分开 | 低负载、最少副本数或固定账单会阻断省钱路径 |
| GPU 同时推进更多有效请求 | 可用 KV 容量与实际批次 | 逻辑 token → 块表 → 非连续物理 KV 块，按需增长、结束后回收 | 尾块仍浪费；更长历史仍占容量且增加注意力读量；耗尽会抢占重算 [1][3] |
| 同样时间完成更多有用计算 | 减少重复工作，改善批次与执行效率 | 前缀命中跳过已有 prefill；请求完成后补入；prefill 分块与 decode 共享预算；后端执行连接到具体 token 与 KV 块 | 无相同前缀则无该项收益；APC 不直接加速 decode；分块预算在 TTFT 与 ITL 间取舍 [2][3] |
| 更多并发转成吞吐而非只增加等待 | 每步时间随批次、上下文与后端变化 | 批次共用权重读入的条件，以及步耗时和延迟目标 | 短上下文权重 IO 主导只是一个条件；计算饱和、KV IO、CPU 或通信可成为新瓶颈 [4] |

层次为「服务产出与成本 → 工作量／显存／执行三个相连因素 → 一个请求、一个 KV 块、一次执行」。总览保留请求 token、批次 token 预算、KV 块表、执行后端、返回 token 和延迟观测的连接；点击下钻时回答更窄的父问题，并保留总览与返回入口。调度只负责其中一条连接。PagedAttention 的内存表示是 vLLM 的辨识性主线；连续批处理、前缀复用和图执行不是 vLLM 独占发明。

成本采用透明记账关系，而非宣传倍率：

\[
Q_{\mathrm{good}}=\frac{N_{\mathrm{completed\ requests\ meeting\ SLO}}}{T},\qquad
C_{\mathrm{request}}=\frac{C_{\mathrm{GPU}}+C_{\mathrm{CPU}}+C_{\mathrm{other}}}{N_{\mathrm{completed\ requests\ meeting\ SLO}}}.
\]

计时窗口为 \(T\)，计数只含同时满足既定 TTFT、ITL／TPOT 等条件的已完成请求；零合格请求时成本显示不可定义。不同请求长度分布不能直接比较请求单价；可另报每百万合格输出 token 成本。这个式子是教学记账定义，不是 vLLM 的性能预测器。

## 首屏与一次关键交互

首屏标题可用「同一块 GPU，为什么能接住更多请求？」。选择**一张相连的资源与执行工作台，加同尺度基线**；不选术语卡片墙，也不让完整队列动画占据首屏。基线明确命名为「每请求最大长度预留＋固定批次的教学基线」，不能代表所有现代竞品。首屏同时出现请求、KV 实际／预留／尾块占用、当前有效批次、重复 prefill 工作，以及延迟目标与成本记账；有来源的测量与结构推导分开。

一个可手算的局部证据：KV 预算为 32 个 token 槽，每请求最多预留 16 槽；四个请求当前长度为 5、9、3、7。基线只能预留两个请求；教学页大小为 4 时，分页占 8＋12＋4＋8＝32 槽，可容纳四个。必须显示「当前容量快照」，后续增长仍可能耗尽；**这不是 2 倍吞吐测试**。

关键交互是把同一服务从「持续并发请求」切到「偶尔一个请求」。它改变到达轨迹，不偷偷改变模型、KV 预算、精度或 SLO。持续负载下，读者追踪空出的块如何允许补入新请求，以及有用批次如何使用执行资源；稀疏负载下，两侧都只有一个请求，更多容量不能被使用。在固定一台付费 GPU、相同合格需求的假设下，成本记账不会凭空下降。点击一个请求可追到块表与下一次执行；未入批请求明确显示等待。其余条件如长输出无前缀命中、长上下文抢占，通过后续预设验证。

交接给实现的模型最小输入为：到达时间、输入／输出长度、可复用前缀、KV 预算与块大小、批次 token 预算、SLO、成本口径及执行耗时依据；派生对象为块映射、重复／新计算 token、活动批次、完成与达标计数。容量可精确推导；毫秒、tok/s 与真实成本收益必须来自标明硬件／版本的测量，或明确标为假设的敏感性模型。当前没有时延曲线，首版不得伪造速度数字；应显示容量变化与待测性能状态。

## 已核验依据与待证事实

1. [原始 PagedAttention／vLLM 论文摘要（2023-09-12）](https://arxiv.org/abs/2309.06180)：动态 KV、碎片与冗余限制批次，分页与共享改善容量。它支持设计动机，不直接证明 2026 年所有配置的收益；本交接不沿用论文倍率。
2. [官方 APC 文档：Introduction / Limits](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)：复用已有前缀以省 prefill；长输出主导或无命中时收益有限。访问日期 2026-10-28，页面标注 2026-10-13。
3. [官方 V1 调优文档：Preemption / Chunked Prefill / Parallelism](https://docs.vllm.ai/en/latest/configuration/optimization/)：KV 不足可重算；分块调度有延迟权衡；增加并行有同步代价。latest 是移动文档，访问日期 2026-10-28。
4. [官方站点 V1 解剖文章：Engine / Benchmarks](https://vllm.ai/blog/2025-09-05-anatomy-of-vllm)：文章明确基于 2025-08-09 的 42172ad，提供组织关系、图执行、goodput 定义及带前提的批次／权重 IO 解释；不将该快照的实现细节当作当前默认。

实现前仍须确认：目标 vLLM 发布版本与模型／后端支持；APC 与图执行实际启用条件；KV 字节构成和运行时预算；代表性请求轨迹、冷暖缓存比例与到达峰值；同质量基线及公平优化；TTFT／ITL 的统计口径和尾部分位；步时随批次／上下文的曲线、CPU 与网络耗时；GPU 计费、最小副本和扩缩容策略。多 GPU、混合／稀疏模型与 P/D 分离只在有对应证据时扩展，不能把单 GPU 推断外推过去。
